# Work Time Tracking App

A small web application for tracking the working time of a company's employees. You can add employees, start and stop a timer with a task description, and see each employee's records and total time for any period. Data is stored in a single SQLite file and survives restarts. It was built as a test assignment for a Programmer role at Falcon AI, with the code written by an AI assistant and reviewed, run and verified by a human. All data in the project is fictional.

## What it does

In the browser you add an employee, select them, type a task and press Start. A live clock shows the running timer, and Stop ends it. Below that, a period picker (today, yesterday, last 7 days, this month, or any two dates, with arrows to step through days) shows the total time of every employee and the detailed records of the selected one. Mistakes produce a clear message instead of breaking the page: a second timer for the same person, stopping when nothing runs, a duplicate or empty name, or an invalid period. A report with no employees or no entries shows zero totals, not an error.

## How to run

You need Python 3.10 or newer.

```
python -m venv .venv
source .venv/bin/activate        # Windows PowerShell: .venv\Scripts\Activate.ps1
pip install -r requirements.txt
uvicorn app.main:app --reload
```

Then open http://127.0.0.1:8000. The interactive API documentation generated by FastAPI is at http://127.0.0.1:8000/docs.

To fill the database with fictional demo data (five employees, a week of entries, one timer still running):

```
python seed.py             # only works on an empty database
python seed.py --reset     # delete everything first, then add demo data
```

The database file is `data.db` in the folder where the server is started. Set the environment variable `TIMETRACK_DB` to use another path.

## Tests

```
pytest
```

The tests cover adding employees (including trimming and duplicate names in any letter case), starting and stopping, the one-timer rule, restarting a timer (stop then start again, and a second start while one is running), period totals with clipping at both boundaries, running timers, an empty report, persistence after a restart of the application, validation errors, the regression cases for the bugs listed below, and the seed script. Service tests use an in-memory database and an injected clock, so they are deterministic. API tests use a temporary database file.

## How it works

The stack is Python with FastAPI and uvicorn, SQLite through the standard `sqlite3` module (no ORM), one plain HTML and JavaScript page with no build step, and pytest with httpx for tests.

```
app/
  db.py        connection, schema, time helper
  service.py   business logic, no HTTP code
  main.py      FastAPI routes, a thin layer that maps service errors to status codes
static/
  index.html   the user interface
tests/         pytest tests
seed.py        fictional demo data
LOG.md         working log: prompts, AI usage, bugs found
```

Business logic lives in `service.py` and takes a database connection as an argument, which keeps it easy to test and explain. The routes only translate HTTP into service calls and service errors into status codes.

### Rules

All times are stored in UTC as strings in one fixed-width format (`YYYY-MM-DDTHH:MM:SS.ffffffZ`), so comparing the strings is the same as comparing the times. Values received from the user are parsed and converted to this format first. The database itself enforces three rules: only one running entry per employee (a unique partial index), an end time never before the start time, and valid employee references (foreign keys, switched on for every connection).

Period totals clip entries to the period boundaries. An entry counts only for the part inside the period, a running timer counts up to the current moment, and the period includes `from` and excludes `to`. An entry that crosses midnight therefore contributes only the hours that fall inside the selected day. The report lists every employee, with zero for those without entries. In the UI the period is chosen in whole local days and converted to UTC before it is sent.

### API

| Method and path | Purpose |
|---|---|
| `POST /employees` | add an employee (`{"name": "..."}`) |
| `GET /employees` | list employees, with the running timer if any |
| `POST /employees/{id}/timer/start` | start a timer (`{"task": "..."}`) |
| `POST /employees/{id}/timer/stop` | stop the running timer |
| `GET /employees/{id}/entries?from=&to=` | entries and clipped total for one employee |
| `GET /report?from=&to=` | total seconds per employee for the period |

`from` and `to` are optional ISO 8601 datetimes (a value without a time zone is read as UTC). Each entry shows its full `duration_seconds` and `counted_seconds`, the part inside the period.

| Situation | Status |
|---|---|
| start while a timer is already running | 409 |
| stop with no running timer | 409 |
| duplicate employee name | 409 |
| unknown employee (including impossibly large ids) | 404 |
| empty or too long name or task | 422 |
| invalid datetime, year outside 1970–2200, or `from` after `to` | 422 |

## AI tools and models used

All code, tests and documentation drafts were written with Claude Sonnet 5.5 (Anthropic) in the Claude app. The human decided the scope, reviewed the code, ran the application and the tests, tried to break it, and made the design decisions. The assistant was also asked to review its own work: the bugs below were found by it sending adversarial requests to the running app, not by manual testing of the interface. The project plan that guided the assistant (design first, small steps, tests together with code, no claims that something works unless it was run) is kept in the repository as the design document, and `LOG.md` records the prompts and decisions as they happened.

The prompts below are quoted as they were typed.

It then wrote the service layer, routes and tests.
4. "I didn't like the period inserter field to filter the days to see what worker did that day. Its to complicated to write on it, user have to pick which number to change and etc. Its inconvenient." The datetime fields were replaced by date pickers, quick buttons and arrows.
5. "This is my gitignore, what should I add. Also could you tell me what bugs should I look for and log them in?" The assistant probed the running application and the five bugs below were the result.
6. "Should we add delete employee button to the ui?" The assistant advised against a plain delete (it risks losing recorded history and needs a decision about existing entries), so it was left as a documented improvement.

## Errors found in the code and how they were fixed

Each was reproduced with a failing test before it was fixed.

1. **A huge employee id crashed with HTTP 500.** A number above the SQLite integer maximum cannot be bound to a query and raised an `OverflowError`. Ids outside the valid range are now treated as "not found" (404).
2. **Extreme dates crashed with HTTP 500.** A value like `9999-12-31T23:59:59-05:00` overflowed while being converted to UTC. The conversion now catches the overflow and the request gets a 422.
3. **Years below 1000 silently broke the time comparison.** `0999-01-01` was accepted and stored as `999-01-01...` without zero padding, which broke the fixed-width format that makes string comparison correct. A report using it showed zero hours with no error. Only years 1970 to 2200 are accepted now.
4. **A name made only of invisible characters was accepted.** A zero-width space passes `strip()`, so a blank-looking employee could be created. Names and tasks must now contain at least one visible character.
5. **There was no length limit.** A 100,000-character task was accepted and would break the page layout. Names are limited to 100 characters and tasks to 500, and the page inputs have the same limit.

Also checked and found correct: twenty simultaneous start requests for the same employee produced exactly one success and nineteen conflicts, so the one-timer rule holds under a race.

## Known limitations

- Duplicate names are detected case-insensitively only for ASCII letters, because SQLite's `NOCASE` collation does not fold other alphabets. "Иван" and "иван" count as different employees.
- In a raw URL a `+` time zone offset must be written as `%2B` (or use `Z`); otherwise it is read as a space and rejected with a 422. The interface always sends `Z`.
- The records table does not refresh by itself while a timer is running (the clock does); it updates on the next action or period change.
- There is no authorization, no roles, and no way to edit or delete records, as the assignment allows.

## Possible improvements

Editing and deleting entries to correct a forgotten timer; deleting or archiving employees while keeping their history (deletion needs a decision about existing entries, so it was not added as a bare button); exporting a report to CSV; showing times in a chosen time zone; pagination for long entry lists; simple authentication and roles; deployment with a hosted database.
